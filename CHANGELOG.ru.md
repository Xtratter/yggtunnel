# История изменений

**Русский** · [English](CHANGELOG.md)

## 0.41 — 2026-10-06

- Журнал соединения теперь сообщает, когда обращение к серверу (пиры, устройства, обёртка, панель сервера…) пошло через Yggdrasil, потому что собственный адрес сервера не ответил, — и получилось ли это или почему нет (например, VPN был выключен). Раньше это было видно только в окне журнала самого обращения, которое пропадает после закрытия

## 0.40 — 2026-10-06

- **Функции сервера работают, если его собственный адрес не отвечает**: получение пиров, устройства, обёртка, панель сервера и всё остальное, что приложение делает по SSH, теперь идёт через ваш узел Yggdrasil, если прямое подключение не удалось (5 с) и известен Yggdrasil-адрес сервера. Это происходит само; VPN (узел) должен быть включён. Отказ в входе или смена ключа сервера по-прежнему показываются как есть
- Для этого в приложении есть небольшой встроенный TCP-стек (только для этих соединений, создаётся при первом использовании): библиотека стала больше на несколько МБ. Трафик туннеля не затронут

## 0.39 — 2026-10-06

- Рефакторинг и ускорение пути пакетов, **в сети ничего не меняется**: байты, уходящие узлам Yggdrasil и серверу, те же, что в 0.38 (сверено побайтно со старым кодом на тысячах случайных пакетов)
- Быстрее сборка пакетов: одно выделение памяти вместо двух, контрольная сумма примерно вдвое быстрее (сборка UDP-пакета 3,8 → 1,7 мкс); меньше выделений для датаграмм от сервера
- Код пакетов вынесен в `packet.go`; `AttachTunnel` разбит на небольшие функции, добавлен тест конфигурации WireGuard
- Сводка в журнале соединения больше не компилирует регулярное выражение на каждой строке

## 0.38 — 2026-10-04

- **Любой сервер можно удалить из списка**: у каждого сервера в «Сервер → Серверы» рядом с «Изменить» есть «✕» — приложение забывает этот сервер на телефоне (на самом сервере ничего не меняется). Раньше удалить можно было только активный сервер, из его карточки
- Настройка обёртки больше не пишет «Сервер готов», если ещё нужен ответ (домен для нового сайта, лимиты telemt, выбор сайта): окно журнала теперь пишет «Ещё один шаг — ответьте в следующем окне»
- Проверено пользователем на новом VPS: настройка по паролю работает, приложение перешло на свой SSH-ключ

## 0.37 — 2026-10-04

- **Настройка сервера по паролю**: в окне сервера появилось «Вход: По паролю / По SSH-ключу»; для нового сервера по умолчанию пароль — то, что обычно выдают с новым VPS. После успешной настройки приложение создаёт свой ключ ed25519, добавляет его на сервер в ~/.ssh/authorized_keys, проверяет вход по нему и дальше входит только по ключу; для root пароль не хранится. Поддерживаются оба способа входа по паролю, которые используют серверы (password и keyboard-interactive); на неверный пароль — понятное сообщение
- Пользователь не root с sudo, которому нужен пароль: пароль хранится зашифрованным и передаётся sudo (sudo -S — только после проверки, что sudo действительно его спрашивает, иначе строка попала бы в скрипт)
- Пароль не попадает в копию настроек на сервере
- Тесты: настройка по паролю на тестовом SSH-сервере (ключ добавлен и проверен, дальше хватает одного ключа, sudo -S для пользователя, неверный пароль); пароль не попадает в копию на сервере

## 0.36 — 2026-10-04

- **Имя на deSEC прямо из приложения**: если на сервере ещё нет HTTPS-сайта, в окне «Сайт для обёртки» появилась кнопка «Создать имя на deSEC». Вставьте токен API deSEC (desec.io, бесплатно) и выберите имя — новое вида myvpn.dedyn.io или под доменом, который у вас там уже есть (vpn.вашеимя.dedyn.io). Сервер заведёт имя, направит его запись A на себя (с минимальным TTL домена), затем поставит nginx, получит сертификат Let’s Encrypt и настроит обёртку, подождав до 3 минут, пока имя заработает. К deSEC обращается сервер (у него всегда есть интернет); токен передаётся ему только через stdin по SSH, хранится на телефоне зашифрованным и не попадает в копию настроек на сервере
- Окно «Сайт для обёртки» показывает собственный IPv4-адрес сервера для записи A
- Тесты: deSEC против имитации API (новое имя, имя под своим доменом, минимальный TTL, чужой домен, занятое имя, неверный токен); токен не попадает в копию на сервере

## 0.34 — 2026-10-04

Единственное, что раньше делалось вручную, — лимит новых соединений на порт 443 с одного адреса в стороннем фильтре (mtpr-synfix) — теперь распознаётся при настройке обёртки, и если он слишком мал для переподключений телефона, выводится предупреждение

## 0.29 — 2026-10-04

- **Исправлено зависание с параллельными каналами** — нашёл отчёт о зависании из 0.28: главный поток ждал в Stop WireGuard, отправитель WireGuard ждал в Write одной из дорожек, а Read этой дорожки заклинило. У дополнительных дорожек оставался MTU Yggdrasil по умолчанию — 1280 (у основного узла 65535); пакеты WireGuard от сервера больше, а на пакет больше MTU Read отвечает «packet too big», записывая изнутри Read, — запись ждёт ironwood, а ironwood ждёт этот же Read. Поэтому каждый большой пакет на дорожке терялся (отсюда и провал скачивания через дорожки в 0.26), а рано или поздно дорожка клинила — и вместе с ней WireGuard и кнопка «Отключить». Теперь у дорожек MTU основного узла; это проверяет тест

## 0.28 — 2026-10-04

- **Мёртвая дорожка больше не используется.** Дорожка помечалась готовой один раз и никогда не снималась: когда её канал обрывался (смена сети, разрыв соединения), каждый третий пакет данных всё равно уходил в неё и терялся, а соединения внутри туннеля вставали — вероятно, это и были «зависания». Теперь каждая дорожка проверяется раз в секунду: канал упал — сразу выходит из работы; поднялся — возвращается, когда ping через неё дойдёт до сервера
- **Отчёты о зависаниях**: сторож раз в секунду проверяет, что главный поток приложения отвечает; после 5 с без ответа стеки всех потоков и горутин сохраняются в files/hang-*.txt, в журнал связи и уходят на ваш сервер (/etc/yggtunnel/diag/)
- **Падения Go сохраняются**: panic или fatal error в ядре на Go пишется в файл, показывается и уходит на сервер при следующем запуске
- Журнал связи → «Отправить отчёт о проблеме»: те же стеки плюс состояние узла и журналы — когда туннель встал, а экран работает

## 0.27 — 2026-10-03

- **Параллельные каналы: по дорожкам идут только данные.** 0.26 с 3 каналами: отдача 24,5–30,3 Мбит/с (1 канал: 15,4–17,6) — лучшая через VPN за всё время, — но скачивание упало до 36–46 (1 канал: 90–128): WireGuard сервера отвечает на адрес, с которого слышал телефон последним, а подтверждения при скачивании шли со всех дорожек — скачивание прыгало между ними и приходило вперемешку. Теперь пакеты WireGuard меньше 400 байт (подтверждения, keepalive) всегда уходят через основной узел, по дорожкам раскладываются только данные

## 0.26 — 2026-10-03

- **Дорожки по очереди**: в 0.25 каждый пакет шёл через наименее загруженную дорожку, а при равенстве побеждал основной узел — очереди же почти всегда пусты, поэтому сервер получил 75,9 МБ через основной узел и только 26,4 и 12,8 МБ через две дорожки, а отдача не изменилась (17,5 → 19,5 / 11,2 Мбит/с). Дорожка, которой достаются лишь излишки, не разгоняет своё TCP-окно. Теперь при равенстве готовые дорожки берутся по кругу — трафик несут все соединения, и их окна растут параллельно

## 0.25 — 2026-10-03

- **Параллельные каналы до сервера** (Пиры → «Параллельные каналы до сервера»: 1–4, по умолчанию 1 — как раньше). Весь туннель шёл одним TCP-соединением; на мобильном аплинке с потерями оно после каждой потери режет окно вдвое и растёт обратно на один сегмент за круг (~1,4 Мбит/с в секунду при 80 мс), поэтому 15-секундный замер отдачи далеко не уходил (диагностика 03.10). С 2–4 каналами телефон поднимает дополнительные узлы Yggdrasil — у каждого свой ключ и своё TLS-соединение до сервера, — и WireGuard отправляет каждый пакет через тот, где меньше всего байт ждёт отправки. Отдельные узлы — потому что сессии Yggdrasil выбрасывают пакеты, пришедшие не по порядку, и пакеты одной сессии нельзя раскладывать по каналам; сам WireGuard перемешивание переносит. Сервер менять не нужно. Экспериментально — сравните отдачу при 1 и при 3–4
- Библиотека маршрутизации Yggdrasil (ironwood) теперь — исправленная копия в go/third_party: считает байты, ждущие отправки по её каналам (22 строки)
- Тесты: вторая дорожка поднимается и одна несёт WireGuard в обе стороны; дорожки с одним адресом остаются разными каналами; счётчик ожидающих байт возвращается к нулю

## 0.24 — 2026-10-03

- **Короткая очередь отправки на канале до сервера**: ядро телефона держало в сокете канала до 1,9 МБ ещё не отправленных данных туннеля — около 4 с очереди на медленном мобильном аплинке с потерями, поэтому при отдаче всё в туннеле получало секунды задержки (пинг под нагрузкой в Speedtest 4150 мс), а TCP внутри проседал. Проверено на ядре этого телефона: в тесте неотправленные данные 1,58 МБ → 32 КБ
- Диагностика: «Очередь отправки канала» — 128 КБ / без ограничения, для сравнения

## 0.23 — 2026-10-03
